## Current optional ClamAV deployment

Browser never installs or starts system antivirus services. Majoris OS may
optionally provide Debian `clamav-daemon` and `clamav-freshclam`, enable signature
updates, and provision an access-controlled Unix socket. Start from
`packaging/clamav/majoris-clamd.conf.example`; use a dedicated scanner group,
mode 0660 and explicit authorised user membership. Never expose an unauthenticated
clamd TCP listener. Configure the GSettings `download-scanner-socket` path to match the OS
service and restart Browser after configuration changes. Check the exact schema
key names before provisioning; the deployed configuration is operator-managed.

Keep Browser's default 64 MiB `download-scanner-max-mib` within StreamMaxLength,
MaxFileSize and total archive/time/memory limits. Raise it only after capacity
review (supported Browser range 1–1024 MiB). `HeuristicAlerts yes` and
`AlertExceedsMax yes` are required to make daemon resource-limit skips explicit;
INSTREAM cannot discover all daemon limits. Such results are incomplete scans.
Maintain freshclam service health and database permissions, monitor failed
updates and disk capacity, and recover a stopped daemon before retrying Scan.
A reported database date older than seven days warns; an absent/unparseable date
is unknown, never proof of current protection. Live capability probes and the
Downloads Check Scanner action recover availability without deleting history.

The separate managed-service implementation and operator contract are in
[services/threat-protection](../services/threat-protection/README.md). Its tests
use local fixtures; no live endpoint or entitlement is claimed. The older
statement below that no backend component exists is historical.

# Engine security maintenance

## Current deployment contract and optional local scanner

The supported distribution model is an authorised Majoris-operated Web Risk service with separately provisioned opaque per-installation/user tokens, or an approved provider provisioning model. Ordinary users must not need personal Cloud projects. No production endpoint, provider entitlement, operator, billing account or backend was supplied here; local fixtures do not qualify a service. A backend is intentionally not invented or deployed.

For the existing managed client contract, provision an HTTPS endpoint without query, fragment or embedded credentials through `managed-threat-endpoint`, set `web-risk-managed=true`, and provision an opaque token (maximum 512 bytes) through Secret Service schema com.majoris.browser.ThreatProvider, attribute provider=managed-web-risk. The direct Google key remains in provider=google-web-risk. The user must independently give informed full-URL consent through the native dialog (`web-risk-consent`); provisioning must not silently grant it. Managed consent is bound to the exact endpoint in `web-risk-consent-target`; an old direct-Google consent or changed endpoint does not authorise disclosure to a new service. Changing mode/endpoint clears the native checkbox. Existing direct-Google consent retains its original fixed-provider meaning. Restart all Browser/app processes for endpoint/mode/consent changes. Keys/tokens are read per check and can be rotated separately.

Requests are GET endpoint?threatTypes=MALWARE&threatTypes=SOCIAL_ENGINEERING&threatTypes=UNWANTED_SOFTWARE&uri=percent-encoded-destination, with Authorization: Bearer per-installation-token. Responses use the existing Web Risk v1 lookup JSON: HTTP 200 `{}` for no known match, or `threat.threatTypes` and RFC3339 `expireTime` for known categories. Return 401/403 for invalid/revoked authorisation, 429/503 plus Retry-After for quota/temporary failure. Never return an empty successful object for an error. Redirects, malformed JSON, unknown categories, excessive responses and TLS errors fail closed. Client timeout/rate/cache rules are unchanged. Only a backend legitimately authorised for Google Web Risk under current commercial/redistribution terms may use this contract and Google advisory attribution.

The accountable operator must supply permitted deployment terms, privacy/retention policy, end-user disclosure, authentication/provisioning/rotation/revocation, per-installation and account quotas, abuse protection, billing, uptime and incident response. Provider Cloud keys belong server-side. Avoid raw URL/token logging, redact query/authentication data, minimise retention, isolate caches and prevent backend SSRF/open-proxy behavior. The service calls its authorised provider, never the destination website. None of these backend controls is claimed implemented by this client contract. A licensed local-list/hash-prefix route would reduce full-URL disclosure, but needs approved list/update distribution, canonicalisation, integrity and ongoing maintenance; no such feed or entitlement was supplied. No non-commercial Safe Browsing substitution is made.

Settings health describes the most recent runtime evidence: disabled = Not Configured; enabled but unconfirmed/missing secret = Unavailable; valid verdict = Active (maximum 60 seconds); timeout, rate/backoff or network outage = Temporarily Unavailable; rejected auth, invalid configuration or invalid provider data = Service Error. Cancellation alone is not a service failure. Cached matches retain their attribution. Live deployment remains unverified.

Optional file scanning uses an already configured local clamd Unix socket, selected in Settings → Downloads (`download-scanner-socket`; blank disables; restart to apply). Browser never installs/starts clamd or freshclam, never invokes a shell scanner, never uses TCP and never uploads files remotely. Majoris administrators must install a supported ClamAV service, maintain official signatures with freshclam, restrict socket access/ownership and configure engine/archive limits (including appropriate AlertExceedsMax behavior). VERSIONCOMMANDS provides capability/version/database date; reported age is advisory, and missing date means freshness unknown. A custom test database is not production malware coverage.

At completion, configured scans enter Scanning and block Open. Results are No Threat Detected (not a guarantee), Known Threat Detected (Open blocked and a native warning), Scanner Unavailable, or Scan Failed. Without configuration, files stay Not Assessed. One scan runs per process; busy completions are marked unavailable and can be retried manually. Files over 64 MiB, symlinks, special files, changed/replaced inputs and protocol failures never receive a clean verdict. Removal/private-session expiry cancels work without resurrecting metadata; user files are retained. Old clean/pending results are invalidated on restart. Executable cautions still apply, and the browser does not offer a permanent malware bypass. The assessment describes bytes at scan time, not future file modifications or full protection outside Browser.

The optional reproducible real-daemon check is `python3 tests/integration/real-clamd-runner.py --clamd /absolute/path/to/clamd --binary /absolute/path/to/download-scanner-test` (add `--library-directory` for an extracted runtime). It uses a disposable config/database and stops its daemon in finally. CI uses a deterministic local protocol fixture, and a disposable Debian clamd 1.4.3 was separately exercised with an original harmless custom hash signature. No real malware or public-service credentials were used. The daemon was stopped and no system package/service was installed. Production official-signature freshness remains the operator's responsibility.


Latest source assessment: [security-assessment.md](security-assessment.md) enumerates the ten unresolved upstream fixes, distinguishes Windows/Mac advisory wording from unproven Linux applicability, and records why the pin was not replaced. `scripts/audit-cef.py` provides a reproducible read-only provenance/index check. The complete required suite now contains 25 groups.

## Google Web Risk configuration

The supported integration is the commercial [Web Risk Lookup API v1](https://docs.cloud.google.com/web-risk/docs/reference/rest/v1/uris/search), not a bundled Google Safe Browsing service. Before activation, obtain an authorised Google Cloud project/account, enable Web Risk, review current [terms](https://cloud.google.com/terms/service-terms), [pricing and quotas](https://cloud.google.com/web-risk/pricing), restrict the key to the intended API/account deployment and establish ownership of billing, rotation and service monitoring. No entitlement or real key was supplied here, and no live API was called.

Open Settings → Advanced → Threat Protection. Enter the key into the password field; it is stored in Secret Service under com.majoris.browser.ThreatProvider/provider=google-web-risk. Confirm the account and full-URL-sharing consent, then save and restart every Browser/app process. Consent explicitly includes query strings, private windows and installed apps. Fragments are excluded; URLs with embedded credentials are refused. A full-URL Lookup service is not a privacy-preserving hash-prefix service. Choose not to enable it if this disclosure is unsuitable. The default remains off with an explicit unavailable status. Disabling/removing the key also requires restart to stop already-running configured processes; revoke the key at the provider for immediate account-level revocation.

The [API key header](https://docs.cloud.google.com/docs/authentication/api-keys-use#using_an_api_key_with_rest) avoids putting the secret in URLs. Navigation checks are async, cancellable and fail closed when enabled. Only a valid no-match response permits the destination. The process limiter reserves checks at one-second intervals and queues ordinary rapid redirects for up to 1.5 seconds within the existing deadline. Excess queueing is cancelled; retry navigation after the interval. Already queued requests also respect a new provider backoff. 429/503 backoff is at least 60 seconds and honours longer Retry-After values up to ten minutes; there are no automatic paid retries. Positive matches are cached in memory by context and full destination hash for at most 60 seconds and never beyond provider expiry; clean/error/unknown responses have no cache lifetime. The native warning follows [Google's warning guidance](https://docs.cloud.google.com/web-risk/docs/user-warnings), including advisory attribution, possible misclassification and no guarantee of protection. Keys and destination URLs are not logged by this module.

Deterministic local HTTPS/Secret Service tests qualify transport, parsing, verdict mapping, query distinction, fragment exclusion, redirect/TLS denial, cancellation, limits, recovery and disabled/missing-key states. They do not establish that a supplied account is entitled or that the live service works. Before release, a consenting maintainer must qualify the real account, Google-provided harmless test URLs, billing/quota failure and rotation, and re-review applicable terms/privacy disclosures. No live blacklist is shipped. Navigation reputation is not downloaded-file scanning; file assessments remain not assessed unless an actual native interruption supplies a supported blocked/malicious/unavailable state. The explicit no-known-file-threat enum is reserved for a future real file verdict and is never inferred from a clean URL.


## Current security baseline and limits

The audited bridge starts CEF with sandboxing enabled and command-line arguments disabled; it does not add no-sandbox, ignore-certificate-errors, disable-web-security, disable-site-isolation or file-origin relaxation switches. Chromium handles mixed-content/origin enforcement with its defaults. Certificate errors are denied, with no bypass UI. Native bindings exist only in certificate-valid HTTPS isolated worlds and are checked against frame/context/current origin; no arbitrary native bridge is exposed to page JavaScript. Unknown permissions are denied. Profiles and temporary grants remain scoped to their owners. The platform fixture additionally observes renderer seccomp filtering/no-new-privileges and exercises invalid TLS, SOP and file-fetch denial. This is a baseline audit, not a penetration test or complete proof of site isolation.

CEF 152's supplied public headers expose no URL-reputation service API or download danger/verdict accessor. `CefDownloadItem` exposes interruption reasons, which Majoris preserves as interrupted, security-blocked or security-check-failed. A failed check is not a malware verdict. The optional Web Risk adapter is implemented but no live account/key has been configured or qualified for this build. Chromium branding and the presence of a content-setting enum are not evidence of active Google protection. Without a configured local scanner, ordinary downloads display **Security: not assessed**; native interruption reasons may supply a malicious/policy-blocked/unavailable state. The optional local clamd adapter described above can assess file contents when configured. Live URL verdicts require the separately authorised Web Risk configuration above.

Live deployment still requires an authorised account, current terms/privacy review, quota/error/rotation monitoring and a consenting maintainer to qualify the service. The implemented adapter and local fixtures do not supply that infrastructure. Google Safe Browsing non-commercial usage is not silently substituted for Web Risk. Download content reputation remains a separate external service dependency; software-opening cautions are not file safety verdicts.

Reviewed API sources: the shipped `cef_download_item.h`, `cef_accessibility_handler.h`, `cef_browser.h`, `cef_task_manager.h` and task structs. Public AX callbacks deliver trees/locations; they do not dispatch node actions or import history. `ExecuteChromeCommand` is not an AX-node action API. CDP Accessibility is an inspection domain, and DOM/coordinate input substitutes would lose native AX semantics. Upstream [Alloy PiP](https://github.com/chromiumembedded/cef/blob/master/libcef/browser/alloy/alloy_browser_host_impl.cc) still rejects windowless hosting (reviewed 18 October 2026); pinned runtime tests independently confirm refusal. The exact SDK source was retrieved in this pass; its explicit OSR PiP and prerender exclusions are recorded in security-assessment.md.

M156 entries are beta and M154 is listed as legacy by the branch policy, so neither was silently substituted as a production fix. **Distribution is blocked pending a fixed supported SDK or a documented applicability/mitigation review.** Passing fixtures do not resolve that security delta.

The shipped SDK README identifies CEF commit `8a0b5b99fd4aac7e353f847685be05577298970c` and Chromium commit `dd78960ccd8a03a2fe1f629543d27783885b78e9`. Archive SHA-256 is `25cf8c95532060fda22c2f85de2e71ba0e0166d344e6741e0062935653efa94f`; publisher SHA-1 is `007ef6e820f2391d63845329e4ca186eec847905`. Bootstrap verifies both. The SHA-256 is a repository integrity pin, not a publisher signature or proof that the engine has all current security fixes.

Before each OS-package update:

1. Review the [CEF build index](https://cef-builds.spotifycdn.com/index.html), [CEF branches](https://chromiumembedded.github.io/cef/branches_and_building.html) and Chromium security releases. Record channel, support status, review date and applicable fixes. Compilation does not establish security support. Resolve the delta recorded above before distribution, and repeat the review at release time.
2. Select an explicit SDK version. Obtain its archive through the publisher, verify available publisher integrity/provenance, independently pin SHA-256, and update VERSION/NAME/SHA1/SHA256 together in `scripts/bootstrap-cef.py`. Retain SDK README commits, licensing and checksums with the release record. Do not replace a live installed engine independently of its package.
3. Run bootstrap into a new directory, rebuild its CEF wrapper, then run `scripts/verify-clean.py --cef-root /absolute/new-sdk`. Requalify C ABI/VAPI and all isolation/security/input/accessibility fixtures; compare codec/EME capability reports rather than assuming Chrome parity.
4. Run `scripts/verify-package.py --cef-root /absolute/new-sdk --output-directory build-packages-UNIQUE`, followed by `scripts/verify-deb.py` against its main package. Record package SHA-256/source revision, exact 25-suite results, resources/notices/sandbox modes, and manual target-desktop qualification. Review any missing optional suite as a failure to qualify.
5. Publish only through the distributing OS's signed package process after open release gates are resolved. Rollbacks must use a separately qualified package and consider profile compatibility. There is no application self-updater, updater daemon or established security-response SLA.

Majoris Browser and its distributing OS/package maintainer must maintain the bundled CEF engine. The current development pin is not a promise of ongoing security support. Do not release an engine pin merely because compilation and fixtures pass.

For each release, the maintainer must review upstream Chromium and CEF security advisories and available supported CEF builds, select an appropriate fixed engine, and record the exact CEF/Chromium versions and review date in the release verification results. Known applicable security fixes block release until incorporated or a documented mitigation is reviewed. This repository has no automated engine updater or established response-time service agreement.

An engine upgrade changes the explicit pin and digest in `scripts/bootstrap-cef.py`. Meson must not download a replacement silently. The bootstrap verifies a repository-pinned SHA-256 plus the publisher's pinned SHA-1 over HTTPS; neither digest is a publisher signature. Record the upstream artifact provenance and any stronger verification available for the replacement. Never weaken sandbox, TLS, origin checks or site isolation to accommodate a new SDK.

Build the wrapper against the selected SDK and requalify C ABI/VAPI calls, subprocess/resource discovery, sandbox operation, persistent versus private contexts, profile leases/deletion, cookies and all storage tests. Run the complete fresh-source suite, package/staged-runtime checks, native Wayland/X11 input and accessibility checks, and the consenting-user Sheets isolation scenario. Update notices and redistribution materials with the shipped SDK. Keep release artifacts tied to their source revision and engine provenance.

Security-sensitive regressions must be fixed and retested before distribution. A passing test suite is evidence for its fixtures and environment, not proof of complete browser security or provider compatibility.
