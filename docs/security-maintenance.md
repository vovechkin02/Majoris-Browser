## Google Web Risk configuration

The supported integration is the commercial [Web Risk Lookup API v1](https://docs.cloud.google.com/web-risk/docs/reference/rest/v1/uris/search), not a bundled Google Safe Browsing service. Before activation, obtain an authorised Google Cloud project/account, enable Web Risk, review current [terms](https://cloud.google.com/terms/service-terms), [pricing and quotas](https://cloud.google.com/web-risk/pricing), restrict the key to the intended API/account deployment and establish ownership of billing, rotation and service monitoring. No entitlement or real key was supplied here, and no live API was called.

Open Settings → Advanced → Threat Protection. Enter the key into the password field; it is stored in Secret Service under com.majoris.browser.ThreatProvider/provider=google-web-risk. Confirm the account and full-URL-sharing consent, then save and restart every Browser/app process. Consent explicitly includes query strings, private windows and installed apps. Fragments are excluded; URLs with embedded credentials are refused. A full-URL Lookup service is not a privacy-preserving hash-prefix service. Choose not to enable it if this disclosure is unsuitable. The default remains off with an explicit unavailable status. Disabling/removing the key also requires restart to stop already-running configured processes; revoke the key at the provider for immediate account-level revocation.

The [API key header](https://docs.cloud.google.com/docs/authentication/api-keys-use#using_an_api_key_with_rest) avoids putting the secret in URLs. Navigation checks are async, cancellable and fail closed when enabled. Only a valid no-match response permits the destination. The process limiter reserves checks at one-second intervals and queues ordinary rapid redirects for up to 1.5 seconds within the existing deadline. Excess queueing is cancelled; retry navigation after the interval. Already queued requests also respect a new provider backoff. 429/503 backoff is at least 60 seconds and honours longer Retry-After values up to ten minutes; there are no automatic paid retries. Positive matches are cached in memory by context and full destination hash for at most 60 seconds and never beyond provider expiry; clean/error/unknown responses have no cache lifetime. The native warning follows [Google's warning guidance](https://docs.cloud.google.com/web-risk/docs/user-warnings), including advisory attribution, possible misclassification and no guarantee of protection. Keys and destination URLs are not logged by this module.

Deterministic local HTTPS/Secret Service tests qualify transport, parsing, verdict mapping, query distinction, fragment exclusion, redirect/TLS denial, cancellation, limits, recovery and disabled/missing-key states. They do not establish that a supplied account is entitled or that the live service works. Before release, a consenting maintainer must qualify the real account, Google-provided harmless test URLs, billing/quota failure and rotation, and re-review applicable terms/privacy disclosures. No live blacklist is shipped. Navigation reputation is not downloaded-file scanning; file assessments remain not assessed unless an actual native interruption supplies a supported blocked/malicious/unavailable state. The explicit no-known-file-threat enum is reserved for a future real file verdict and is never inferred from a clean URL.


## Current security baseline and limits

The audited bridge starts CEF with sandboxing enabled and command-line arguments disabled; it does not add no-sandbox, ignore-certificate-errors, disable-web-security, disable-site-isolation or file-origin relaxation switches. Chromium handles mixed-content/origin enforcement with its defaults. Certificate errors are denied, with no bypass UI. Native bindings exist only in certificate-valid HTTPS isolated worlds and are checked against frame/context/current origin; no arbitrary native bridge is exposed to page JavaScript. Unknown permissions are denied. Profiles and temporary grants remain scoped to their owners. The platform fixture additionally observes renderer seccomp filtering/no-new-privileges and exercises invalid TLS, SOP and file-fetch denial. This is a baseline audit, not a penetration test or complete proof of site isolation.

CEF 152's supplied public headers expose no URL-reputation service API or download danger/verdict accessor. `CefDownloadItem` exposes interruption reasons, which Majoris preserves as interrupted, security-blocked or security-check-failed. A failed check is not a malware verdict. The optional Web Risk adapter is implemented but no live account/key has been configured or qualified for this build. Chromium branding and the presence of a content-setting enum are not evidence of active Google protection. Ordinary downloads display **Security: not assessed**; native interruption reasons may supply a malicious/policy-blocked/unavailable state. There is no file-content scanner. Live URL verdicts require the separately authorised Web Risk configuration above.

Live deployment still requires an authorised account, current terms/privacy review, quota/error/rotation monitoring and a consenting maintainer to qualify the service. The implemented adapter and local fixtures do not supply that infrastructure. Google Safe Browsing non-commercial usage is not silently substituted for Web Risk. Download content reputation remains a separate external service dependency; software-opening cautions are not file safety verdicts.

Reviewed API sources: the shipped `cef_download_item.h`, `cef_accessibility_handler.h`, `cef_browser.h`, `cef_task_manager.h` and task structs. Public AX callbacks deliver trees/locations; they do not dispatch node actions or import history. `ExecuteChromeCommand` is not an AX-node action API. CDP Accessibility is an inspection domain, and DOM/coordinate input substitutes would lose native AX semantics. Upstream [Alloy PiP](https://github.com/chromiumembedded/cef/blob/master/libcef/browser/alloy/alloy_browser_host_impl.cc) still rejects windowless hosting (reviewed 18 October 2026); pinned runtime tests independently confirm refusal. Online fetches of this SDK's exact source commit were unavailable, so upstream master review is not represented as exact-pin source qualification.

## Reproducible update record

Audit result, 18 October 2026: the [CEF publisher index](https://cef-builds.spotifycdn.com/index.json) lists `152.0.14+g8a0b5b9+chromium-152.0.7977.167` as the latest Linux M152 stable SDK (minimal archive published 17 October). The [CEF branch policy](https://chromiumembedded.github.io/cef/branches_and_building.html) identifies M152 as Extended. Google's [15 October advisory](https://chromereleases.googleblog.com/2026/10/extended-stable-update-for-desktop_01598036246.html) lists 10 security fixes in `.169` for Windows/Mac. This does not establish which fixes affect the Linux embedding; their applicability/backports must be resolved. There is no `.169` Linux M152 artifact in the checked index. M156 entries are beta and M154 is listed as legacy by the branch policy, so neither was silently substituted as a production fix. **Distribution is blocked pending a fixed supported SDK or a documented applicability/mitigation review.** Passing fixtures do not resolve that security delta.

The shipped SDK README identifies CEF commit `8a0b5b99fd4aac7e353f847685be05577298970c` and Chromium commit `dd78960ccd8a03a2fe1f629543d27783885b78e9`. Archive SHA-256 is `25cf8c95532060fda22c2f85de2e71ba0e0166d344e6741e0062935653efa94f`; publisher SHA-1 is `007ef6e820f2391d63845329e4ca186eec847905`. Bootstrap verifies both. The SHA-256 is a repository integrity pin, not a publisher signature or proof that the engine has all current security fixes.

Before each OS-package update:

1. Review the [CEF build index](https://cef-builds.spotifycdn.com/index.html), [CEF branches](https://chromiumembedded.github.io/cef/branches_and_building.html) and Chromium security releases. Record channel, support status, review date and applicable fixes. Compilation does not establish security support. Resolve the delta recorded above before distribution, and repeat the review at release time.
2. Select an explicit SDK version. Obtain its archive through the publisher, verify available publisher integrity/provenance, independently pin SHA-256, and update VERSION/NAME/SHA1/SHA256 together in `scripts/bootstrap-cef.py`. Retain SDK README commits, licensing and checksums with the release record. Do not replace a live installed engine independently of its package.
3. Run bootstrap into a new directory, rebuild its CEF wrapper, then run `scripts/verify-clean.py --cef-root /absolute/new-sdk`. Requalify C ABI/VAPI and all isolation/security/input/accessibility fixtures; compare codec/EME capability reports rather than assuming Chrome parity.
4. Run `scripts/verify-package.py --cef-root /absolute/new-sdk --output-directory build-packages-UNIQUE`, followed by `scripts/verify-deb.py` against its main package. Record package SHA-256/source revision, exact 24-suite results, resources/notices/sandbox modes, and manual target-desktop qualification. Review any missing optional suite as a failure to qualify.
5. Publish only through the distributing OS's signed package process after open release gates are resolved. Rollbacks must use a separately qualified package and consider profile compatibility. There is no application self-updater, updater daemon or established security-response SLA.

Majoris Browser and its distributing OS/package maintainer must maintain the bundled CEF engine. The current development pin is not a promise of ongoing security support. Do not release an engine pin merely because compilation and fixtures pass.

For each release, the maintainer must review upstream Chromium and CEF security advisories and available supported CEF builds, select an appropriate fixed engine, and record the exact CEF/Chromium versions and review date in the release verification results. Known applicable security fixes block release until incorporated or a documented mitigation is reviewed. This repository has no automated engine updater or established response-time service agreement.

An engine upgrade changes the explicit pin and digest in `scripts/bootstrap-cef.py`. Meson must not download a replacement silently. The bootstrap verifies a repository-pinned SHA-256 plus the publisher's pinned SHA-1 over HTTPS; neither digest is a publisher signature. Record the upstream artifact provenance and any stronger verification available for the replacement. Never weaken sandbox, TLS, origin checks or site isolation to accommodate a new SDK.

Build the wrapper against the selected SDK and requalify C ABI/VAPI calls, subprocess/resource discovery, sandbox operation, persistent versus private contexts, profile leases/deletion, cookies and all storage tests. Run the complete fresh-source suite, package/staged-runtime checks, native Wayland/X11 input and accessibility checks, and the consenting-user Sheets isolation scenario. Update notices and redistribution materials with the shipped SDK. Keep release artifacts tied to their source revision and engine provenance.

Security-sensitive regressions must be fixed and retested before distribution. A passing test suite is evidence for its fixtures and environment, not proof of complete browser security or provider compatibility.
